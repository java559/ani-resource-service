**Res 在全部资源领域负责自己的权限、业务身份、配置与资源台账、引用、幂等、并发、原生对象提交、结果登记和管理生命周期。资源提供方及依赖服务负责其契约内的执行和公开结果。Res 直接消费这些约定结果，不重复证明组件内部实现，不接管其常规控制、垃圾回收和故障修复。**

适用范围：Res 的全部现有领域、存量实现和未来能力，以及相应设计、代码、后台任务、合同、配置、测试和执行 agent。更新日期：2026-11-09。任何新增或恢复的逻辑，只要越过已确定的职责边界，即使名为“安全检查”“修 CI”“兼容”“兜底”或“增强可靠性”，都必须阻断。简化同时保留 Res 自己的身份、台账、并发和真实完成责任。

# 一 全域适用与试点定位

VM 与 Network 是这套机制的首批试点。Res 的其他现有领域及未来能力，都应按同一职责边界设计、审核和整改；是否进入专项迁移，不影响该边界的适用。ACC 方案用于界定相邻服务与 Res 的交互责任，不把 ACC、Gov 或监控职责划入 Res。

全域原则已经确定，存量实现按领域推进迁移。已完成、已验证的范围以具体代码版本和执行记录为准；Network 与 VM 的试点完成不等于整个 Res 已完成推广。后续任何领域的新增、修改或恢复都不得增加越权依赖，尚未整改的旧实现也不享有例外。

全域原则规定职责边界和禁止事项；领域合同在这些边界内规定具体权威字段、状态转换和完成条件。旧领域文档、旧测试或旧实现与原则冲突时，应同步收敛，不能据此保留越权机制。修订职责边界不能由执行 agent 以“更安全”或“更通用”为由自行决定。

# 三 必须遵守的十二条原则

## 1 管理职责必须完整保留

按资源实际作用域维护稳定身份，核验适用的权限、租户、owner、输入范围、资源引用、唯一占用和业务影响约束。Kubernetes 对象使用其实际 cluster、namespace、UID 等身份；其他提供方使用相应稳定标识。平台级或集群级资源不机械增加 tenant 或 namespace。对存在的并发与异步执行风险，沿用适用的 expectedVersion、幂等、lease、命令或通知代次、closing、resourceVersion 等保护，防止认错对象、重复执行和过期写回；不要求每个接口拥有全部字段。原生 API 对特定配置更新的确认按领域合同使用，不扩展成通用 generation 门槛。

这些检查必须能说明保护了哪一项 Res 业务约束。它们不能扩展成下游链路的签名、摘要、读集、水位或完整性证书。简化不得绕过已有认证、租户隔离、当前权限或对象归属。

依据：网络规格第 1、3 节；VM 包 PHASE1-REMEDIATION 第 1 节；ACC 包 01-plan 第 3 节。

## 2 原生结果直接消费 平台业务范围单独检查

每类事实都明确约定的公开权威来源，并按当前对象身份和当前操作消费。Res 保存自己的业务意图、引用与映射，提供方声明自己的执行结果；不要求全部事实来自同一个组件，也不靠拼接内部细节另造权威。试点中，网络对象按逐类合同使用 Ready、phase、Initialized 等公开状态或管理结果；Snapshot 使用自身状态和 included/excluded；Restore 使用自身 complete 和具名输出；CDI 复制使用匹配目标 DV 的 Succeeded。其他领域映射到自身原生契约，不复制这些字段名称。

Res 检查结果是否满足平台已明确的业务要求。例如 VM 整机恢复需要确认 Required 业务卷都被快照包含；真正 Restore 需要停止态、当前版本、影响摘要和必要确认。不能沿 SnapshotContent、VolumeSnapshot、PV、CSI 再证明原生成功，也不能把地址非空、生成 Service 正常或节点健康拼成第二套 Ready。“业务要求”必须能指向具体产品约束，不能成为重复证明底层正确性的改名。

“管理请求能否受理”“原生动作是否完成”“平台映射是否登记”“旧对象是否清理完毕”是不同判断。原生结果可信，不代表这些判断可以合并成一个成功布尔值。

依据：[网络准入口径](https://github.com/zhangzhe-ctrl/ani-resource-service/blob/d7c344a02a7e3e1f7c4221286ec82bc33428bac4/docs/plans/network-management-simplification.md)；[VM 规格](https://github.com/zhangzhe-ctrl/ani-resource-service/blob/ab189b99a5bcfc482a0208102ee3328c9a60ae27/docs/specs/vm-mvp.md)；VM 包 R02、R03、R07。

## 3 禁止恢复重复证明体系

禁止为二次裁决下游正确性、替代原生状态或延长本服务完成边界而新建或恢复 proof、Covers、关系闭包、审计续签、全量独立对拍、下游清场证明、历史 attempt 完整退出、CRI 或 journal 补证，以及专供这些证明使用的表、通道、任务和常驻 agent。正常业务身份签名、内容校验和原生 API 并发条件仍按各自合同保留。

禁止换名恢复：把 proof 改名成 certificate、snapshot digest、readset、freshness gate，或者把旧校验搬进 helper、adapter、SQL、默认配置、重试或隐藏开关，仍属于同一越权逻辑。判断依据是实际用途和调用依赖，不是名字。

Network 试点已明确删除 ErrObservationPending 等旧共享观察合同。不能为了旧测试或旧错误映射重新定义它；其他领域同样不得用兼容或重试恢复已废止职责。真实来源未同步或连接中断的错误，按本领域合同处理，不能仅因名称相似而误删。

依据：[PR 57 实施方案的删除清单与合并前检索要求](https://github.com/zhangzhe-ctrl/ani-resource-service/blob/d7c344a02a7e3e1f7c4221286ec82bc33428bac4/docs/plans/network-management-simplification.md)；VM 包 R04；ACC 包 01-plan 第 11 节。

## 4 每个动作只依赖完成该动作必要的事实

各领域分别确定受理、执行、结果登记、引用释放、清理、辅助刷新和展示所需的最小事实集合。某条路径只依赖完成当前动作所必需的条件，不捆绑无关资源的就绪、健康、诊断或历史全集。VM 试点中，Start、Stop、Restart 和根 VM Delete 使用自身生命周期所需的 VM/VMI 信息，无关磁盘、介质、backend 或 PV 诊断失败不阻止提交；需要当前 Pod 的网络、日志等功能仍应选择正确目标，不能把多 Pod 或 launcher 歧义伪装成没有运行对象。

删除来源引用、刷新库存、展示地址和监控查询也应按各自事实推进。辅助信息未就绪，只影响真正依赖它的功能；不能传播为整个资源失效。

这种拆分必须保留独立更新责任。PR 66 的最后修正已经明确：异步磁盘准备复用现有持久观察任务刷新 UID、Preparation 和容量，存储读取错误不污染电源观察，也不改变已经完成的电源操作。已经准备完成的盘不因此增加持续存储审计。

依据：[VM 规格 S08](https://github.com/zhangzhe-ctrl/ani-resource-service/blob/ab189b99a5bcfc482a0208102ee3328c9a60ae27/docs/specs/vm-mvp.md)；[PR 66 两项局部修正](https://github.com/zhangzhe-ctrl/ani-resource-service/blob/ab189b99a5bcfc482a0208102ee3328c9a60ae27/docs/execution/records/VM-PHASE1-20261106/PHASE1-REPORT.md#pr66-local-fixes-20261107)。

## 5 只更新实际取得的事实 明确区分缺失与错误

| 观察情况 | 正确处理 |
| - | - |
| 原生状态明确成功或失败 | 按该对象、该次操作和本领域规则映射 |
| 超时、403、连接错误、列表失败或不完整 | 不能当作 NotFound、空集合或清理完成 |
| 成功读取返回空地址或撤回结果 | 按字段合同更新，不因旧值非空而永久保留 |
| 本次轻量观察没有读取磁盘或介质 | 不得用空数组覆盖现有台账 |
| 正在采用的必需输出尚未存在 | 保留等待或依赖未就绪，不能伪造结果可用 |
| 已登记历史清理对象真实消失 | 按其生命周期收尾，保留必要历史身份 |

网络读取错误保留最后成功的状态、原因、地址和时间。VM 对真实观察源断连按其既有诊断规则表达 Unknown；健康同步但没有新事件不自动失效。ACC 当前集合采集失败不清空占用。可选物理 bytes 的未知表示等字段特例沿原合同处理，不扩成所有字段一律清零或一律回退旧值。

依据：网络规格第 1、2 节；VM 规格 S08；ACC 包 01-plan 第 5、6 节。

## 6 持久执行与输出交接属于 Res 的核心责任

对需要持久异步执行的动作，复用本领域已有的操作记录、任务、并发保护和 checkpoint，保存已受理意图、确定的外部对象标识、已知身份、输出和清理责任。请求结果未知时认回同一次提交，不换名字新建另一资源猜测成功；旧 worker 和晚到事件不能覆盖新版本、删除意图或当前映射。简单同步操作无需为了“全域统一”增加 operation、worker、lease 或持久任务框架。

凡是原生动作会产生需要 Res 接管的业务输出，都应在销毁结果载体前完成具名输出和责任的持久交接；取消也遵守同一边界。VM Restore 和未来 Clone 是这种模式的实例：先登记公开输出及清理责任，再结束唯一承载结果的原生对象，之后按已登记对象清理。未知清单不等于零产物；不得先删结果载体，再通过全 namespace 扫描、标签猜测或孤儿控制器补回来。

原生 complete、平台映射提交、producer 退出、来源引用释放和目标清理分别按各自合同推进。VM 一阶段允许的 Pending/WFFC 输出，不得被额外的“所有 PVC 必须 Bound”条件卡住；采用当前恢复结果时，必需 PVC 仍须存在。其他领域按自身结果可用性合同定义必要条件，不把这一状态组合套用于全部资源。

依据：VM 包 R03；[VM 规格的 Snapshot 与 Restore 条款](https://github.com/zhangzhe-ctrl/ani-resource-service/blob/ab189b99a5bcfc482a0208102ee3328c9a60ae27/docs/specs/vm-mvp.md)。二阶段 Clone 相关要求是未来设计约束，不是当前已实现能力。

## 7 删除结束于自己的管理责任 不延伸到物理清场

删除请求被提供方接受不等于当前管理动作已经完成。每个领域须完成其既有合同中直接负责的对象、关系和结果交接，不因根对象消失就丢弃其他已登记责任。VM 试点的责任包括适用的 VM/VMI、相关运行对象、业务 DV/PVC、Secret/Job、Snapshot/Restore、当前与退休盘，以及自己的 Network/SG 等引用。仍被当前对象引用的资源、未结束的 producer、未交接的输出或真实身份冲突不能被忽略。

明确的管理责任完成后，不继续向下证明组件内部或物理世界已清空。在 VM、Network 试点中，这意味着不等待 PV、CSI handle、SnapshotContent、VS/VSC、KCN 自动子资源、VIP 物理回收或驱动退出证明。该边界按对象归属与动作用途判断，不构成对所有领域的资源类型黑名单。平台 Deleted 不代表介质已物理擦除，ACC RELEASE_CONFIRMED 也不代表驱动或操作系统已被平台证明完成回收。

VM 删除及消费者终结路径先确认原根 VM、VMI 对象已不存在，且不存在相关非终态 Pod，再发布消费者 closed 并请求 Network Release。Network 按当前消费者管理关系完成释放，不等待 KCN 子资源清场；consumer closed 不能反过来等待 Network released。普通 Stop/ForceStop 保留 VM、盘和 Attachment 预留，不按删除路径释放网络占用。整 VM 删除 operation 仍需完成自己的盘、快照、producer 和引用等剩余责任。

Res 业务及关系的终结任务按其合同退休，旧观察、迟到结果和进程恢复不重新打开它们。只删除数据库业务行、清空 cleanup 或批量改成功，不能替代实际完成。

依据：网络规格第 2 至 4 节；VM 规格 S10；VM 包 R05；ACC 包 01-plan 第 1 节。

## 8 身份保护必须准确 不能把正常消失误判为替换

始终保留原对象的作用域与稳定身份。Kubernetes 对象不按同名自动接管新 UID，也不为了继续删除而更新成新对象 UID；其他提供方的同名替换按对应稳定标识处理。消失、尚未读取身份和实际发生身份替换是不同事实，结果按当前动作的合同判断。

PR 66 最后修正的具体边界是：对同 kind、namespace、name 的已登记恢复输出，本轮 UID 为空时保留已知 UID；两个非空 UID 不同仍拒绝。历史输出消失可继续清理，不要求恢复已经消失的对象。真正采用当前输出时，必要对象仍须存在。

不能把某个场景推广成“不同 UID 一律删除成功”或“空 UID 一律通过”。PR 57 删除自己的旧网络对象时，同名不同 UID 表示原对象已结束，且不得碰新对象；正在采纳 VM 恢复输出时，真实 UID 替换仍是冲突。

依据：[PR 66 两项局部修正](https://github.com/zhangzhe-ctrl/ani-resource-service/blob/ab189b99a5bcfc482a0208102ee3328c9a60ae27/docs/execution/records/VM-PHASE1-20261106/PHASE1-REPORT.md#pr66-local-fixes-20261107)；网络规格第 3 节。

## 9 部署支持条件与既有对象身份分开

平台支持的组件能力、存储模式、运行时前提和受管配置，在相应的部署、配置或首次创建入口明确验证。不要把一次环境支持验证变成每次动作或观察时的重复完整验收，也不能因删除验证代码就承诺尚不支持的能力。领域合同要求的真实动态条件仍在相应入口验证；固定能力验收与当前业务条件不可混用。

新默认配置对存量和新资源的影响按既定领域合同处理，不能用当前默认值否定已经受理的意图或已登记身份。VM 试点中，新默认 StorageClass、SnapshotClass 等只按其合同影响新创建；既有资源继续依据自己的 UID、归属、冻结配置和原生结果处理，不因此失效或重建。

VM 镜像试点仍验证内容格式、可读性、SHA 与结果归属，受限 Job 仍只读访问。删除的是每次上传通过写打开实验证明运行时只读的 ReadOnlyProof 门槛，不是取消内容检查和只读配置。推广时同样保留本领域真实的输入与内容约束，删除重复的环境证明。

依据：VM 包 R06、R08；VM 规格镜像条款及 S08。

## 10 组件内部故障交组件或已落实运维 不进入常规补偿

对组件拥有的内部资源，Res 常规执行路径不推导、枚举和追删，不剥离第三方 finalizer，不篡改底层策略以强行完成。VM 与 Network 试点中，这包括 CDI prime、scratch、uploader 内部对象、PV reclaimPolicy 和底层网络规则。底层问题交组件或既有运维处理，Res 保留真实未完成状态和具体原因。对本来已明确属于 Res 管理的对象或自己的 finalizer，按既有授权和完成合同正常处理；此条不新增任何管理权，也不允许通过重新命名归属接管组件内部资源。

PR 66 的 R09 已有实际验证过的限定运维接替。这不构成 Res 自动处理 finalizer 的长期授权：历史处置仅针对明确授权的终态 uploader，使用 UID/resourceVersion 条件，只处理对应 foregroundDeletion 并保留其他 finalizer。

将来移交类似已知故障责任时，组件修复或既有运维接替必须实际可用；不能删除补偿后遗失已有业务清理责任，也不能把旧补偿移进常驻 helper、repair 服务或隐藏开关。

依据：[CDI 限定运维手册](https://github.com/zhangzhe-ctrl/ani-resource-service/blob/ab189b99a5bcfc482a0208102ee3328c9a60ae27/docs/runbooks/vm-image-cdi-handoff.md)；VM 包 R09；[PR 66 R09 结果](https://github.com/zhangzhe-ctrl/ani-resource-service/blob/ab189b99a5bcfc482a0208102ee3328c9a60ae27/docs/execution/records/VM-PHASE1-20261106/PHASE1-REPORT.md)。

## 11 当前分配 业务生命周期 配额和监控各用各的事实

全域推广中，当前分配、业务生命周期、配额账本与监控各自保留权威来源和完成条件。ACC 方案的当前分配来自 Kubernetes 与 Volcano；Res 作为业务 owner 管理自己的生命周期；Gov 按既定配额契约占退额；Prometheus 保存实际使用量历史。不能用任一账本的一个状态代替其他账本的完成条件，也不能借 Res 全域整改改变相邻服务职责。

就该方案涉及的 GPU 配额而言，创建占额、业务最终删除退额的规则不变。ACC binding 退出当前集合不自动触发 Gov 退额；Usage ENDED 也不能把仍存在的当前分配清掉。不得再增加 ACC 退款审批、CRI 退出证明、设备解绑证明或历史水位补验。

实际 GPU 使用量与承诺分配量不同，监控无数据也不同于观测到零。监控缺失和可选展示失败不得成为资源创建、删除、释放或配额的新门槛；不为监控历史再建 owner 历史证明库。CPU、内存、存储等其他配额规则不从本条自动推导。

依据：ACC 包 01-plan 第 2、5、6、11 节及 05-acceptance C05、C14、D03。

## 12 删除旧机制必须同时修改实现 合同和测试

废弃机制应从实际运行依赖中退出：入口、领域方法、字段消费、SQL、后台任务、配置、调用方、注释和测试同步收缩；专用于越权逻辑且无其他正当用途的权限一并收回。不能删除函数后保留旧测试，再以修 CI 为由加回旧接口、错误类型或证明字段。

已明确允许保留的历史诊断、业务记录、in-flight checkpoint 和 protobuf 字段号，按各自方案处理；保留字段号或读旧值不授权继续运行旧证明。不得自行增加双 writer、双运行模式、旧 proof fallback、静默空成功 RPC 或历史证明重放。

验证聚焦受影响的身份、并发、状态、清理责任和禁止的调用边界，完成必要回归和仓库要求即可。STATIC、单元、数据库集成、真实部署结果分开记载；不把方案当实现、不把本地测试当现场通过，也不因提交 SHA 变化机械重跑与改动无关的全量验收。

依据：VM 包 PHASE1-REMEDIATION 第 4、5 节；ACC 包 01-plan 第 7 至 11 节；PR 57 的实际删除清单。前次 #58、#59 审核所见的旧 FullStop 审计和 ErrObservationPending 依赖，正是本条需要阻止的回退形式。

# 四 不能机械统一的领域差异

| 事项 | 已定边界 | 禁止的错误推广 |
| - | - | - |
| Ready | 网络管理受理不追加 Provider Ready 门槛；快照能否完整恢复仍消费原生 Ready 和 Required 覆盖 | 把所有 Ready 条件都删掉，或给所有动作统一加 Ready 门槛 |
| informer | 网络采用精确事件通知和目标 GET；VM 状态观察可读取已同步且连接健康的标准索引 | 要求所有领域必须禁用缓存，或统一另建一轮全量核验 |
| LIST | 正常列表接口、informer 初始 LIST/relist、ACC 获准的当前集合采集保留 | 以删除或恢复为由扫描全 namespace、全群下游对象来做清场证明 |
| 时间与重试 | 请求超时、lease、故障退避、VM 断连诊断、ACC 当前容量 freshness 按本领域合同保留 | 恢复网络 proof TTL，或把“简化”解释成删除所有超时和周期任务 |
| 终态 | Res 已结束业务与关系不被旧事件复活；ACC 当前分配投影可反映新的合法分配事实 | 把 ACC 的当前投影语义套成 Res Deleted 可以自动重开 |
| 根对象消失 | 删除路径按原身份确认消失后，结束对应原对象的删除；聚合动作仍完成自己的其他责任 | 因根 VM 不见就丢掉业务盘、引用或未登记输出；或继续向下证明物理回收 |
| 身份变化 | 禁止误操作同名新对象，具体结果按当前动作判断 | 不同 UID 一律当成功，或一律追删、接管 |
| 作用域与执行工具 | 使用资源实际作用域和稳定身份；异步任务按需要复用既有持久执行 | 给所有模块强加 tenant、namespace、Kubernetes UID、lease 或 worker |
| 直接管理对象 | 按既有职责和权限区分业务对象与组件内部对象 | 把 PV、Node、Service 等按类型全部禁用，或反过来借全域整改扩大管理权 |
| 旧字段与历史 | 必要业务历史、已登记身份、既有 checkpoint 可按确定方案保存 | 为兼容运行两套证明，或借简化清空全部业务历史 |

依据：网络规格；VM 规格 S08、S10；ACC 包 01-plan 第 5 节、02-data-and-capacity 第 4.3、6.2 节。

# 五 全域推广与存量整改

所有后续变更立即按全域原则审核；存量按领域或一组直接相关的动作逐步迁移。每批明确触达的管理链路与完成范围，既不扩大为全 Res 一次性重写，也不等待其他领域全部迁移后才交付已完成的整改。尚未处理的越权逻辑应在既有整改任务中明确，不继续扩展、复制或激活。

## 先明确当前领域的管理合同

在现有领域规格或整改任务中，简要说明本次直接管理的对象及身份、各项事实的公开权威来源、各动作的最小依赖、完成与删除边界，以及必须保留的台账、引用、并发和输出交接。VM 与 Network 提供判断示例；具体字段、状态、时间条件和观察方式按本领域契约确定。此说明用于设计和代码审核，不形成运行时注册表、证明数据或审批流程。

## 按四步完成每批整改

1. **核对职责。** 从实际调用和数据依赖找出本次范围内的合法管理责任、越权证明和无关门槛，明确应保留与应删除的行为。识别直接管理对象，不能按资源类型批量删除逻辑。

2. **保留业务连续性。** 保存已有意图、稳定身份、在途输出、业务引用和清理责任，复用合适的现有执行机制。必要的数据迁移按该领域实际状态设计，不增加旧机制双写、双运行或 proof fallback。

3. **完整移除越权依赖。** 同步处理生产入口、后台任务、字段消费、配置、无其他用途的权限、调用方、合同和测试。组件内部修复交回组件或已落实的运维途径，不把旧补偿搬进新 helper。

4. **验证并记录实际范围。** 验证相关操作成功与失败路径、身份替换、并发及迟到结果、读取失败、输出交接和自己的清理完成；只选择本次改动涉及的风险与仓库必要检查。记录对应版本、验证层次及尚未完成的具体事项，不因提交变化机械重跑无关验收。

## 完成标准

一个领域或动作范围完成推广，应同时满足：合法管理行为仍完整；越权逻辑及其运行依赖已退出；无关辅助失败不阻塞主流程；自身身份、输出与清理责任不丢失；合同、测试和实现一致。减少代码量、消除报错或“原生状态显示成功”都不能单独替代这些条件。

设计确定、代码合入、针对性验证和实际部署分别记录。全 Res 推广完成的判断须覆盖实际领域与管理路径，不能由两个试点的通过推导；状态放在已有计划和实施记录中维护，不另建全局验收控制器、证明账本或常驻审计系统。

# 六 后续设计与 PR 审核判断表

以下问题适用于 Res 所有领域的设计、功能、修复、测试、配置和存量整改 PR；不等待该领域完成专项迁移才开始遵守。直接在既有设计和 PR 审核中判断，不新增证明库、审批服务或运行时门禁。

| 审核问题 | 判断与处置 |
| - | - |
| 新 guard 保护哪项 Res 业务约束 | 能指向适用的权限、身份、输入、引用、并发或本次真实完成则保留；只有“再确认底层正确”则阻断 |
| 操作是否访问了无关资源或历史全集 | 无本次直接契约依赖的，删除该依赖；不要扩大读取权限解决问题 |
| 是否拼出第二套 Ready 或清场证明 | 即使仅测试、辅助函数或 SQL 中存在，也不得恢复已废止机制 |
| 原生完成后是否仍等内部子资源或物理回收 | 按该对象的既定完成边界收口，保留自己的业务清理 |
| 辅助刷新或监控失败是否阻塞主流程 | 没有真实依赖则拆开执行和错误投影 |
| 是否丢失已知对象身份、输出或清理责任 | 不允许以简化为由清空台账、提前成功或重建猜测 |
| 旧事件能否覆盖新版本或复活终态 | 保留适用的版本、并发、关闭意图和原身份保护，拒绝越期写回 |
| 测试和旧领域文档是否仍要求越权机制 | 同步修正冲突合同和错误期望，不能将旧文档或测试当作豁免 |
| 是否借推广增加统一框架或跨域控制 | 不引入与当前业务需要无关的第二套 observer、状态机、控制器或数据存储；现有越权依赖按整改范围移除，业务数据按确定的迁移方案处理 |
| 是否把试点细节机械套到其他领域 | 按实际作用域、原生公开状态与合法管理对象重新映射，不强加无关字段或资源类型禁令 |

本批新增、修改或继续依赖的路径一旦越权，必须阻断当前方案或 PR，指出具体动作、依赖和影响，整改后才能通过。未整改存量、已有旧测试、实现更方便或“更安全”“更通用”都不能成为放行理由。本批未触及且不依赖的其他存量问题，纳入既有整改任务，不成为本批的全局验收前置，也不因此被认定合规或获得保留豁免。整改保留 Res 自己的真实业务责任；执行 agent 不得借冲突自行扩大目标、接管其他服务或启动无关领域重写。

# 七 可直接加入后续任务的约束

> 本任务遵守 Res 全域管理职责与简化原则，适用于当前领域的存量与新增实现。Network PR 57 和 VM PR 66 是已完成试点，不限制适用范围，也不要求照搬其字段、状态机或观察实现。
>
> 先明确当前动作直接管理的对象、约定权威来源、最小依赖和完成边界。Res 保留适用的权限、作用域、稳定身份、业务台账、引用、幂等、并发、自己的原生声明、输出交接与真实完成；直接消费提供方和依赖服务的公开契约。
>
> 禁止重复证明组件内部正确性、关系闭包、审计续签、下游物理清场、CRI/journal 补证、内部对象追删和剥离第三方 finalizer。禁止换名、测试、兼容分支、后台 helper 或“修 CI”恢复越权机制；旧领域合同不得豁免。
>
> 按资源和动作实际需要使用身份、版本、租约和 checkpoint。受理、原生完成、映射登记、引用释放和目标清理各按合同推进；读取失败不当作对象消失，未知输出不当作零产物，旧结果不覆盖新意图或重开终态。
>
> 主流程只依赖必要事实；辅助刷新承担自己的更新责任，诊断和监控不追加管理完成或占退额门槛。状态、超时、集合采集和具体可用性条件保留本领域必要语义。
>
> 优先复用本领域既有实现；需要持久异步执行时沿用合适的任务与并发机制，不为全域推广新建统一 observer、通用状态机、证明数据库或常驻治理服务。同步调整实现、合同、配置、权限、注释与测试，完成相关必要验证并记录实际版本与范围。任何越权都必须阻断，也不得以简化为由丢失 Res 自己的业务责任。

# 八 文档维护与引用

通用原则保留一份权威版本。纳入 Res 仓库时，放入既有正式合同目录，由 AGENTS.md 和后续任务引用；领域规格只维护在该边界内的具体对象、状态、完成条件及必要差异，实施记录只说明实际完成范围。旧合同与测试中的冲突语句随对应整改收回，不复制出多份可能互相分叉的全域规范，不新增平行状态合同或自动治理系统。
